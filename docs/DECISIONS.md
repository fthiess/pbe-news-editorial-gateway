# PBE News Editorial Gateway — Decision Log

ADR-style record of what was decided, why, and when. Append-only: a change of direction is a new entry that names what it amends or supersedes; the only edit allowed to an old entry is an italic "*Later updated by: …*" trailer. `D*` = design decisions, `N*` = implementation notes. **"Forrest's call"** marks a genuine fork that Forrest decided. Start from [`DECISIONS-INDEX.md`](DECISIONS-INDEX.md).

## Session 1 — Requirements and direction (2026-10-29)

A requirements Q&A between Forrest and Claude, ending in the first PRD draft.

### D1 — Mechanism: a purpose-built remote MCP server, registered as a claude.ai custom connector
Claude reaches Ghost through the **Gateway**, a remote MCP server we host. Its tools are shaped around editorial tasks (read an article, create a draft, set an image's alt text), not a generic pass-through to the Ghost Admin API. The Ghost credential and every safety rule live inside the Gateway.
**Why:** A claude.ai custom connector *is* a remote MCP server, so "a connector" and "an MCP server on our own host" were one option, not two. The real question was where the credential and the guardrails live. Three alternatives were rejected. (a) Sessions calling the Ghost API directly need the credential where the session can read it, so keeping it out of the chat would be a convention, not a guarantee, and it works only in Claude Code. (b) A local stdio MCP server has the same limit, plus it runs only on Forrest's workstation. (c) Community Ghost MCP servers are generic pass-throughs: they would put a third party's code in front of a write credential, with none of our guardrails. A remote server is the only option that serves Duet (no shell, no disk) and cloud Routines, and the only one where "never publish" and "never delete" are code, not instructions.

### D2 — Consumers: Duet, Claude Code, claude.ai web, cloud Routines, and the Linter
The Gateway must be usable from Claude Duet, Claude Code, claude.ai on the web, and scheduled cloud Routines. It must also be usable from the planned PBE News Linter as a programmatic client, if doing so is efficient. The Linter's own design is a separate project.
**Why:** Forrest sees immediate uses on all four Claude surfaces. Duet itself suggested the connector route, which strongly suggests (but doesn't prove) that Duet can use claude.ai connectors. The Linter needs the same read and edit operations, so designing them once avoids a second Ghost integration and a second credential.

### D3 — Scope: an editorial access layer, not an administrative one, and not the assistant editor (Forrest's call)
**In scope:** reading posts and pages with all their metadata, creating drafts, editing drafts and their metadata, and (D12) looking up brothers in Book. **Out of scope:** the design of the "assistant editor" itself, meaning what Claude does with these tools (TK sweeps, readiness checks, intake judgment, editorial status tracking, project management). Also out are all administrative functions: members, tiers, newsletters, email sends, settings, themes, integrations, staff users.
**Why:** The Gateway is plumbing. TK sweeps and readiness checks need nothing beyond complete read access, so they belong to the assistant-editor work that sits on top. Editorial status lives outside Ghost: Forrest tracks it in a spreadsheet and doesn't want it in Ghost, and Ghost(Pro) can't be modified anyway. Keeping administrative functions out removes whole classes of harm.

### D4 — Ghost identity: a dedicated "Claude" staff user with the Editor role (Forrest's call)
The Gateway authenticates to Ghost as its own staff user, named Claude, with the **Editor** role, using that user's staff access token. It takes the third and last staff slot on the Ghost(Pro) plan. The other two belong to Forrest and the backup editor.
**Why:** Compared with Forrest's administrator credentials or an integration Admin API key, a dedicated Editor user (1) attributes every change to "Claude" in Ghost's revision history, (2) can be revoked without touching Forrest's own login, and (3) can't reach members, settings or billing. Ghost's docs say a staff token acts with exactly its user's role permissions. The cost is the last staff slot, and no further human editor is on the horizon. Contributor accounts don't help here, because a contributor sees only its own drafts. ⚠ The Editor role can still publish and delete posts, so D7's refusals in the Gateway stay load-bearing. ⚠ *Unverified:* exactly which Admin API endpoints an Editor token can reach. Test on staging before relying on it.

### D5 — Hosting: Cloud Run with Secret Manager, in its own GCP project (Forrest's call)
The Gateway runs on Cloud Run, scaling to zero, with the Ghost token in Secret Manager readable only by the Gateway's service identity. It gets its own GCP project (one per environment), separate from Book's.
**Why:** The alternative was gladstone, Forrest's GCP VM, which already runs Caddy and ghost-staging. But gladstone is a shared, multi-tenant machine: it hosts many unrelated sites, and more than one person has shell access. A weakness in any neighbor would expose whatever else the machine holds. The most valuable credential in the system shouldn't share a machine with unrelated tenants. Cloud Run removes OS patching, gives built-in logging, costs pennies at this volume, and repeats Book's proven deploy and release pattern. The costs are a cold start of a couple of seconds after idle (Book makes the same trade) and a small persistent store for OAuth state. A separate project limits the blast radius in both directions.

### D6 — Human authentication: Google sign-in against an allow-list; several human editors share one Claude credential
Every caller is authenticated. Connector access uses OAuth with Google sign-in, restricted to an allow-list of accounts. Forrest is the only user today, and the backup editor is expected to join, so the design admits several humans. All of them work through the single Claude Ghost identity (D4) — one Claude editor collaborating with the human editors — and the Gateway records which human was behind each action.
**Why:** An authless connector URL with write access to the newsletter would be a public write endpoint. Google sign-in reuses accounts the editors already have. One shared Claude identity fits the staff-slot limit and Forrest's model of Claude as a single assistant editor. Recording the human preserves accountability that the shared Ghost identity would otherwise lose.

### D7 — Write policy: drafts are Claude's, everything else is read-only (Forrest's call)
Claude may make **any edit to a draft**, post or page, without restriction. It may make **no edit to anything that isn't a draft** (published or scheduled). The Gateway has no operation that changes an article's status, deletes anything, or sends email. When Forrest wants Claude's help with a published article, he unpublishes it himself, has Claude work on the draft, and republishes it. Forrest also takes regular backups of the site's content.
**Why:** Three alternatives were considered and dropped as more complicated than they're worth. (a) Proposals that Claude stores in the Gateway and that Forrest approves on a Gateway web page, out of the model's reach. (b) Approval through the client's per-tool permission prompts, which depend on client features we can't inspect for Duet. (c) "Option 3", briefly agreed in the same session: published articles editable, but with their public identity (status, visibility, slug, email flags) frozen. Forrest's rule replaces all three. Ghost's own draft/published switch becomes the Claude-proof guardrail. It is simple to state, simple to enforce, needs no approval machinery, and makes "yes, please make that change" just work on drafts. The race between a status check and a write is closed by D8. ⚠ *Verify on staging:* does unpublishing and republishing preserve `published_at` (Forrest orders articles within a section by it)? And does republishing the lead article, the only one ever emailed, avoid a second send?

### D8 — Concurrency: every write carries the version it read; collisions are never blindly retried
Every update sends the post's `updated_at` from the read it was based on, so Ghost rejects it if anyone saved in between. On a collision the Gateway never retries blindly: the caller re-reads, then re-applies a mechanical change or reports the conflict. This is built in from the first write path, not added later.
**Why:** Conflicts are unlikely while Forrest drives every session, but likely once Claude works more autonomously. Ghost already provides the collision check, so the cost is just carrying the version through, while retrofitting it later would touch every write path. It also closes D7's race: if Forrest publishes a post between the Gateway's draft check and its write, the publish changes `updated_at` and the write is rejected. Locks and editing windows aren't needed and are out of scope.

### D9 — Change feed: on request only in the MVP; no webhooks
The Gateway answers "what changed since cursor X?" by querying Ghost for posts whose `updated_at` is later than the cursor, and labels changes it made itself using its own log. It doesn't receive Ghost webhooks in the MVP.
**Why:** Duet is the intended consumer, and connectors are request-and-response, so nothing could receive a push anyway. Querying on request meets the need with no Ghost integration to configure, no event store, and no debouncing (Ghost fires `post.edited` on every editor autosave). The cost is that deletions aren't seen, which matters little because the Gateway never deletes. Webhooks stay an option for later. Forrest wants the Linter triggered by Claude or by him, not automatically, which also argues against push for now.

### D10 — Intake: the caller supplies HTML, and the Gateway creates the draft through Ghost's own HTML conversion
To create a draft from a submission, the calling Claude extracts the article as HTML from whatever arrived (email body, Word, Google Doc, PDF), and the Gateway creates the draft through Ghost's server-side HTML-to-Lexical conversion. The Gateway doesn't parse Word, PDF or other source formats.
**Why:** Forrest's experience is that select-all, copy and paste from any source format into the Ghost editor produces a correct article about 98% of the time. The clipboard carries HTML, and the editor converts it, so the server-side conversion is the API equivalent of that paste. Extracting from source formats is the messy, judgment-laden part, and the calling model is good at it (it reads PDFs natively, and Word and Google Docs convert to HTML cleanly). HTML is lossy for *editing* an existing post that contains cards, but it is the right input for *creating* one. ⚠ *Unverified:* whether the server-side conversion matches the editor's paste quality. Test early on staging with real past submissions.

### D11 — Images: upload and placement are deferred; reading images and editing alt text and captions are in the MVP
Uploading new images and placing them in articles is deferred past the MVP. Until then, intake leaves a TK marker where each image belongs (for example `[TK image: harvard-bridge.jpg — caption: …]`) for Forrest to resolve in the Ghost editor. The MVP does include reading images already in Ghost (returned as resized pictures a model can see) and editing their alt text and captions, including the feature image's.
**Why:** Image handling is likely the most complex part of the project. Images arrive embedded in Word files, as separate attachments, or behind Drive and Dropbox links. Placing them means either reproducing their position from the source or making an editorial decision. And moving multi-megabyte files through a model's tool calls is impractical. Forrest doesn't want the Gateway to have Gmail access. The TK marker reuses his existing workflow. Writing alt text, though, is one of the two biggest time sinks in his editing (D15), and it needs only reads and small edits.

### D12 — Book: the Gateway reaches Book through service-to-service Google identity, and Book's rules decide what it sees (Forrest's call)
The Gateway gives Claude a way to resolve a name ("who might James Smyth '84 be?", using Book's fake exemplar brother) to candidate brothers from Book. It authenticates to Book with a Google-signed identity token for the Gateway's service account, so no Book credential is stored anywhere. Book's own visibility rules, the projection a brother-role viewer gets, decide what the Gateway can see. Which Book endpoint serves this is open: Book's existing `GET /api/roster` (Book D58/D78/D112), whose authentication is built but whose payload is still a stub, or a new server-side search endpoint. That fork is decided at the Book ticket's plan gate (**OFC-484**).
**Why:** Canonicalizing names, and linking them to Book profiles, is the other of the two biggest time sinks (D15). Routing it through the Gateway means the Linter and every Claude client need no Book credential of their own. Both Gateway and Book run on GCP, so keyless service-to-service identity is available. Book already enforces privacy by server-side projection, so the Gateway inherits it rather than re-implementing it. Book's name search runs in the browser today, so a search endpoint would mean porting the matcher to the server, while the D58 roster was designed for exactly this caller.

### D13 — Logging: every Gateway action is logged, for troubleshooting
The Gateway logs every action it takes: who called it, from which client, which operation on which article, and the outcome. The token, and article bodies beyond what troubleshooting needs, are never logged.
**Why:** Forrest's requirement, mainly for troubleshooting. Whether each write's prior state is also saved, to make undo easy, is an open question in the PRD. Forrest likes the idea but was concerned about size.

### D14 — Judgment tasks are Claude's, not the Linter's: alt text (Forrest's call), and finding names in prose for Fall 2026
Writing alt text comes out of the Linter: the Linter stays deterministic code, and the Claude session that runs it writes the alt text, using the Gateway's image read. For the Fall 2026 issue, Claude sessions also do name canonicalization directly (find names in the prose, resolve them through D12, edit the draft), so the Gateway doesn't depend on the Linter, which hasn't been started.
**Why:** Alt text needs a model. Putting one inside the Linter would add an Anthropic API key, a separate API bill and non-reproducible output to a tool whose value is being algorithmic. Finding names in free text is also judgment-heavy, and a Claude session can do it with the Gateway's tools today. That takes an entire unstarted project off the critical path for the Fall issue. The Linter can later make name handling cheaper and more consistent.

*Later updated by: D17 (the Fall 2026 clause no longer applies; who canonicalizes names for Spring 2027 is open); D18 (the Linter canonicalizes names).*

### D15 — MVP definition and phasing (Forrest's call)
Name canonicalization (with Book profile links) and image alt text are, by Forrest's definition, the MVP: without them the Gateway isn't worth building before the Fall 2026 issue. The MVP is **Phase A**, built for Claude Code. It contains reading, image reading, the two narrow edits those tasks need (replace a span of text, adding a link; set an image's alt text and caption), metadata edits, the draft-only policy, collision checks, Book lookup and logging. **Phase B**, after the Fall issue is published, adds OAuth for the claude.ai connector, bringing Duet, web and Routines. Draft creation from HTML (D10) and the change feed (D9) are stretch goals for Phase A, and general editing and image upload come later. Approved with Forrest's "go ahead" on 2026-10-29.
**Why:** Forrest is away 2026-10-31 to 11-11, the content deadline is 11-22, and publication is by 12-10. That leaves about eight working days to build. Every Fall-issue need above is served from Claude Code. The OAuth flow a connector needs is the riskiest, most security-sensitive single component, and keeping it off the deadline's critical path is the main schedule lever. Phase A keeps every guardrail server-side: the Ghost credential never leaves Cloud Run in either phase. The two edit types are also far narrower than general card-preserving editing, which is the hardest technical problem in the project.

*Later updated by: D17 (target moved to Spring 2027; Phases A and B merged into one MVP).*

### D16 — Repository: public, named `pbe-news-editorial-gateway`; "Gateway" for short (Forrest's call)
The project lives in its own public GitHub repo, `fthiess/pbe-news-editorial-gateway`, like Book, under the MIT license. Its internal shorthand is "Gateway". Linear work goes in project PBE-Gateway (team Techgnosys).
**Why:** Same posture as Book: the code has nothing to hide, and its safety must not rest on secrecy. Being public puts the "no secrets, no brother names" invariants in `CLAUDE.md` on the critical path.

## Session 2 — Replan after PRD review (2026-10-30)

### D17 — The Gateway leaves the Fall 2026 critical path and targets Spring 2027 (Forrest's call); one MVP replaces Phases A and B
No substantial work happens on the Gateway until the Fall 2026 issue is published. Forrest then returns to it with the aim of using it in editorial production for the **Spring 2027** issue. For Fall 2026, he gets alt text by pasting images into Claude Haiku and pasting the results into Ghost, and he canonicalizes names with a separate small tool, either a Python script with a web interface or a Chrome extension. Neither depends on the Gateway. This amends D15 and the Fall 2026 clause of D14. Consequences:
- **One MVP, not two phases.** Everything previously in Phase A and its stretch goals, plus the claude.ai connector (OAuth), is one MVP for all Claude clients. FR-52, the Linter's identity, waits until the Linter exists. General editing, image upload and webhooks stay after the MVP.
- **Review and travel-window questions close.** The design gets the methodology's full adversarial review, and there is no autonomous build in November.
- **Who canonicalizes names for Spring 2027 is open** (PRD Q8). D14's alt-text decision stands.
- D14's reasoning that alt text needs a model is unchanged. Forrest's test adds a useful data point: Claude Haiku wrote good enough alt text for typical PBE News images.
**Why:** Forrest's parallel projects and personal commitments over the next six weeks or so make the November build unrealistic. The interim workflows are still a big improvement on Spring 2026 and he's comfortable with them, so the Gateway isn't needed for the Fall issue. The two-phase split existed only to keep OAuth off that deadline's critical path, and its Phase A needed a temporary local helper for Claude Code. With the deadline gone, that split would mean building a throwaway authentication path for no benefit, and Duet, the client that motivated the project, would still wait. The merge into one MVP is Claude's recommendation from the replan, carried out under Forrest's instruction to update the feature triage. It is his to reverse.

*Later updated by: D18 (Forrest confirmed the single MVP; Q8 closed; FR-52 moves into the MVP).*

### D18 — The Linter does name canonicalization (Forrest's call); its identity and the whole roster join the MVP
Name canonicalization is the Linter's job, working as a Gateway client: it matches an article against Book's roster and applies the fixes to the draft. A mention it can't resolve to one brother is left for Claude or Forrest. This closes PRD Q8 and replaces D14's and D17's open position on names; alt text stays out of the Linter (D14). Forrest also confirmed the one-MVP merge in D17. Two requirements follow: FR-52, the Linter's non-human identity, moves into the MVP, and a new FR-33 lets a programmatic client fetch the whole roster, which is the bulk-pull-and-match-locally design Book's D58 already specifies. The Fall 2026 canonicalizer stays separate: it works from a local export of roster data, so it needs nothing from Book's API or the Gateway.
**Why:** Forrest wants one consistent answer, and canonicalizing a name against a known roster is the kind of mechanical, repeatable fix the Linter exists for. ⚠ Consequence: the Linter hasn't been started, and the Spring 2027 goal of names working through the Gateway now depends on it, so it needs scheduling alongside the Gateway. The Gateway can go to production without it, but only alt text and the other Claude-driven work would then benefit.
